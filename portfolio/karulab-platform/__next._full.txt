<p>L'ingénierie logicielle contemporaine souffre d'un mal récurrent : une simple interface de gestion devient 500 Mo de conteneurs Node, 1 500 paquets npm imbriqués et un pipeline de build fragile.</p>
<p>Notre principe directeur : <strong>le minimalisme architectural au service de la résilience</strong>. Chaque brique doit pouvoir tourner sur un serveur modeste ou une appliance locale, se déployer en secondes et se diagnostiquer sans diplôme d'architecte.</p>
<h2>Ce Que Nous Construisons Avec Ce Stack</h2>
<ul>
<li><strong>Le panel Kaly</strong> (en développement actif) : application Go stdlib + HTMX + MongoDB — waitlist, leads, parc de box, événements, grille tarifaire. Un binaire, une base, zéro build frontend.</li>
<li><strong>Kady-UI</strong> : notre design system — librairie de web components publiés sur un registry npm privé (Forgejo), Storybook déployé, pour que Go+HTMX, Next.js et les box aient la même pâte graphique.</li>
<li><strong>ci-shared</strong> : les workflows CI Forgejo mutualisés entre tous nos repos (Go et Node : build, lint, tests, release) — la complexité de CI est versionnée à un seul endroit, pas recopiée repo par repo.</li>
<li><strong>hermes-base</strong> : l'image Docker de base de nos agents IA, avec harness par profil — la même rigueur appliquée à l'infra d'agents.</li>
</ul>
<h2>L'Architecture Type</h2>
<pre><code>┌────────────────────────────────────────────────────────┐
│                FRONTEND HYPERMÉDIA (HTMX)              │
│    HTML sémantique rendu serveur, 0 bundle npm         │
└──────────────────────────┬─────────────────────────────┘
                           │ HTTP
┌──────────────────────────▼─────────────────────────────┐
│                 BACKEND (GOLANG STDLIB)                │
│   Binaire statique unique · net/http · goroutines      │
└──────────────────────────┬─────────────────────────────┘
                           │ Driver mongo-driver
┌──────────────────────────▼─────────────────────────────┐
│                 PERSISTANCE (MONGODB)                  │
│   Leads, événements, configs box, audit logs           │
└────────────────────────────────────────────────────────┘
</code></pre>
<ul>
<li><strong>Go stdlib d'abord</strong> : le routeur, les templates <code>html/template</code> (échappement natif), les workers en goroutines. Les dépendances externes sont comptées — le panel n'en a qu'une, le driver Mongo.</li>
<li><strong>HTMX plutôt qu'un framework SPA</strong> : les mises à jour dynamiques ciblées se font en fragments HTML rendus serveur. Pas de hydration, pas de state management, pas de node_modules côté client.</li>
<li><strong>MongoDB</strong> : modélisation documentaire pour ce qui est documentaire (événements, configs hétérogènes), index sur les chemins de requête réels.</li>
<li><strong>Déploiement conteneur</strong> sur Coolify, build direct depuis le Dockerfile, CI qui ne fait que tester et relâcher des tags.</li>
</ul>
<h2>Les Vrais Chiffres, Quand Ils Existeront</h2>
<p>Nous ne publions pas de « p99 en 12 ms » d'un service qui n'est pas encore en production. Ce qui est vérifié aujourd'hui : le panel compile en un binaire unique, ses tests passent en CI, et ses pages se passent totalement de JavaScript applicatif. Les mesures de performance viendront des environnements réels — box pilotes comprises — et seront publiées avec leur méthode de mesure.</p>
<h2>Bénéfices Attendus (et vérifiables)</h2>
<ul>
<li><strong>Surface d'attaque réduite</strong> : pas de chaîne d'approvisionnement npm sur le runtime serveur, échappement HTML natif Go.</li>
<li><strong>Déploiement en secondes</strong> : un conteneur, une variable d'environnement de connexion Mongo, prêt.</li>
<li><strong>Frugalité</strong> : le stack vise les machines edge — ce qui tourne sur un mini-PC client tourne aussi sur un VPS à 5 €.</li>
</ul>
